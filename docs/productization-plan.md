# MultiApp 产品化执行方案与 UI 重设计计划

## 0. 约束与前提

- 当前环境：无真机，仅可进行本地构建、静态验证与 UI 方案落地。
- 设计方向：基于 Apple Design（响应、直觉操控、弹性动效、半透明材质层级、空间一致性、可理解状态）转译为 Android Compose 可实现方案。
- 默认语言：Simplified Chinese；回复避免过分夸赞，优先准确性。

## 1. 项目现状摘要（基于仓库当前证据）

- 技术栈：Kotlin + Jetpack Compose + Hilt + Material 3。
- 架构基线：ARCHITECTURE.md 定义 A/B/C/D 四层边界，UI 不得直接依赖 Host owner 或 InstanceManager；当前 LauncherScreen 已通过 ViewModel + LauncherEffectBus + 专用 use-case 保持边界。
- 测试基线：README.md 记录全量测试 2181+，BUILD SUCCESSFUL。
- UI 现状：3 个主页面（Launcher / AppManager / Settings）已具备核心功能，但距离“产品级体验”仍有差距：反馈层级、边界状态说明、动效节奏、错误恢复路径、信息密度控制。

## 2. 产品化阶段目标

### Alpha（当前阶段 → 目标）
- 产品可演示：入口清晰、核心任务可完成、错误可恢复。
- 工程可交付：文档可追溯、构建可复现、关键路径有自动化测试。
- 体验可感知：反馈即时、状态可读、操作可撤销。

### Beta（需要真机后）
- 真实性能/兼容性验证（安装、启动、多实例切换、权限弹窗链路）。
- 真机特有能力闭环（见能力矩阵的 device-proof 类项）。

### GA（成熟）
- 安全边界与异常恢复完整可审计。
- 关键路径性能与稳定性指标达标（crash-free、ANR-free、冷启动、多实例并发）。

## 3. UI 重设计原则（Apple → Android Compose 转译）

1. 即时反馈：按钮在 pointerDown 就产生可感知状态变化；长按/拖拽保持连续更新。
2. 状态可读：每个页面必须有 4 种状态视图：Loading / Empty / Error / Content；错误信息需指出原因、影响范围、下一步动作。
3. 弹性动效：优先 spring 弹性动画；避免死板固定时长；只在用户“抛掷/拖拽”场景增加微弱 overshoot。
4. 空间一致性：弹窗、底部抽屉从触发源方向出现并原路返回；导航层级清晰可回溯。
5. 材质层级：标题栏/抽屉使用半透明模糊材质表达层级；避免轻材质叠轻材质导致对比度崩塌。
6. 信息密度克制：先呈现关键身份与状态，次要信息按需展开；避免信息轰炸。
7. 无障碍与减动效：支持 ReduceMotion 与高对比模式；在减动效下仍保留状态变化反馈。
8. 可验证性优先：UI 改造必须可构建、可测试；不做无法本地验证的“拟真”交互。

## 4. 页面重设计方案（第一轮产品化改造）

### 4.1 Launcher（主入口）

- 信息架构：
  - 顶部：产品标题 + 汇总状态（实例数、存储占用、最近一次创建时间）。
  - 主体：实例网格（仅核心身份字段：名称、包名、版本、最近打开）。
  - 浮动：创建入口（FAB 或底部主操作）。
- 关键交互：
  - 创建流程：轻触即响应 → 底部抽屉表单 → 提交后即时插入列表并反馈成功。
  - 删除流程：二次确认 + 明确删除后果（实例数据不可恢复）。
  - 长按：弹出操作菜单（打开/详情/删除/导出占位）。
- 状态与错误：
  - 空态：图文引导“还没有实例”，主操作按钮突出。
  - 错误态：展示失败原因与重试；不得静默吞错。

### 4.2 AppManager（实例管理）

- 信息架构：
  - 列表卡片：实例主信息 + 状态徽标（运行中/停止/异常）。
  - 展开详情：依赖项、能力支持状况、最近操作。
- 关键交互：
  - 启动/停止/打开详情三个主操作触达路径最短。
  - 详细信息可折叠，默认低密度。
- 状态与错误：
  - 若当前能力存在不支持项，使用统一“能力状态说明”组件，而非文本堆叠。

### 4.3 Settings（设置）

- 信息架构：
  - 分组：身份模板、存储与缓存、高级（当前仅占位说明）。
  - 设备身份字段说明：哪些字段会影响宿主对外暴露身份。
- 关键交互：
  - 字段变更即时反馈；关键变更具备“确认/回退”路径。
- 状态与错误：
  - 读取失败、写入失败、校验失败三类需明确文案与重试策略。

## 5. 工程任务清单（批次化）

### 批次 A：文档与基线（可全离线）
1. 建立本执行方案文档（本文件）。
2. 在三个 Screen 的代码头部增加“状态视图契约”注释（4 种状态）。
3. 抽取公共 UI 原子：状态徽标、空态组件、错误状态卡。

### 批次 B：第一轮 UI 改造（可全离线）
1. Launcher：顶部汇总栏 + 空态引导 + 弹性动画基础。
2. AppManager：统一能力状态说明组件 + 低密度展开详情。
3. Settings：分组卡片与字段说明；关键变更确认路径。

### 批次 C：验证与收口（可全离线）
1. 本地 Gradle 构建验证（debug）。
2. 关键路径单元/UI 测试补充（至少覆盖空态/错误态切换）。
3. 截图对比记录（可选，需要可运行截图管线时再补）。

### 批次 D：真机门槛（需设备）
1. 真实安装/启动/多实例/权限弹窗链路。
2. 性能基线：冷启动、首次创建实例耗时、内存占用。
3. 能力矩阵中 device-proof 类项完成闭环。

## 7. 当前风险与规避

- 风险：无实机下误把“静态说明”当“能力闭环”。
  - 规避：UI 文案必须区分“功能可用/部分支持/需真机验证”。
- 风险：过度设计导致改造膨胀。
  - 规避：第一轮只做“可构建、可测试、可证明”的产品化变化。
- 风险：动效引入体验不稳。
  - 规避：先用最小 spring 方案，禁止长阻塞动画和复杂依赖。

## 8. 结论

在“无实机”的现实约束下，项目仍可推进到“产品可演示 + 体验可控 + 验证可复现”的成熟阶段。
下一步应执行“批次 B”第一轮 UI 改造，并以“构建通过 + 三种非正常状态可展示 + 动效策略统一”作为本轮完成门槛。
